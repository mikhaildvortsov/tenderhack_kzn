# Research: Автозаполнение характеристик СТЕ по КТРУ

## R1. Данные КТРУ (факты из разведки)

- `data/КТРУ/xml_all/nsiKTRUNew_all_actual_*.xml` — 82 файла, ~982 МБ, 81 465 позиций
  (`oos:position/oos:data`), namespace `oos=http://zakupki.gov.ru/oos/types/1`.
- Позиция: `code`, `version`, `name`, `OKPD2{code,name}`, `status` (ACTIVE), `applicationDateStart`,
  `applicationDateEnd?`, `OKEIs/OKEI{code,name}`, `NSI` (classifiers, standarts),
  `characteristics/characteristic`, `parentPositionInfo`, `rubricators`.
- Характеристика: `code`, `name`, `type` (1 качественная, 2 количественная), `kind`
  (1 неизменяемая заказчиком, 2 выбор одного, 3 выбор нескольких), `actual`, `isRequired`,
  `choiceType` (1 единств., 2 множ., 3 неизменяемый), `values/value`:
  либо `qualityDescription` (текст), либо `OKEI` + `valueFormat` (N|A) + (`rangeSet/valueRange`
  {`minMathNotation` greater|greaterOrEqual, `min`, `maxMathNotation` less|lessOrEqual, `max`}
  | `valueSet/concreteValue`).
- Встречается несколько версий одного `code` → брать максимальную `version`.

**Decision**: потоковый `lxml.etree.iterparse` по `{oos}position`, `elem.clear()`; фильтр по
префиксам ОКПД2 из `etl/categories.py`; запись в SQLite; затем сборка индекса.
**Rationale**: файлы большие, iterparse держит память O(позиция). SQLite — переносимо, без сервера.
**Alternatives**: PostgreSQL (избыточно для read-only 20 тыс. позиций), pandas-read_xml (память).

## R2. Скоуп категорий (префиксы ОКПД2)

**Decision** (стартовые значения, ETL-агент проверяет и корректирует по статистике):
- `clothing`: `14.` (одежда), `15.12` (сумки/рюкзаки — есть в «Одежда.xlsx»), `15.20` (обувь).
- `furniture`: `31.0` (мебель), `25.99.1`/`32.99.` — только если в выгрузке «Мебель.xlsx» есть
  сейфы/стойки (сейфы `25.99.21`).
- `tools`: `25.73` (ручной инструмент), `28.24` (механизированный ручной инструмент),
  `26.51` (измерительные — только если подтверждается выгрузкой), `25.94` (крепёж — нет).
**Rationale**: в презентации три категории; ОКПД2 — надёжный признак отрасли.

## R3. Выгрузки xlsx

- Лист1: `ID СТЕ | Наименование СТЕ | Модель | Производитель | Страна | Характеристики`,
  где «Характеристики» = `Название значение [ед] | ...` (~100 тыс. строк на файл). Кода КТРУ нет.
- Лист2: справочник характеристик по КПГЗ (`Название характеристики`, тип, значения, единица).
**Decision**: использовать (a) как словарь синонимов названий характеристик и значений,
(b) как источник реальных описаний для eval по категории/извлечению, (c) частоты значений.
Ground-truth КТРУ для eval строим синтетически из самого КТРУ (R9).

## R4. Нормализация текста

**Decision**: lower, `ё→е`, унификация кавычек/тире, `0,5→0.5`, разделение «30см»→«30 см»,
`660х420х350` → три числа с меткой габаритов, исправление раскладки (токен латиницей, который
через карту клавиатуры EN→RU даёт слово из словаря КТРУ → замена + issue `layout`),
лемматизация pymorphy3 с LRU-кэшем. Позиции символов (spans) сохраняются через карту
offset’ов к исходному тексту.

## R5. Поиск кандидатов

**Decision**: документ позиции = `name`×3 + `okpd2_name` + значения качественных характеристик;
лемматизированные токены; BM25Okapi по всем позициям скоупа; затем бонусы: точное совпадение
леммы головного существительного названия (+), совпадение категории. Опечатки: токен запроса,
отсутствующий в словаре, заменяется ближайшим (rapidfuzz `WRatio`/`Levenshtein`, порог 85,
длина ≥ 4) → issue `typo`. Top-K = 200 для сужения.
Опционально: e5-small re-rank top-50 (feature flag `USE_EMBEDDER`), включать только при
измеримом приросте на eval.
**Alternatives**: только эмбеддинги (хуже на кодах/числах, медленнее), Elasticsearch (тяжело).

## R6. Извлечение и унификация характеристик

**Decision**:
1. Количественные: regex `число [-–до] число? единица` → (значение/интервал, единица).
   Единица → ОКЕИ через `etl/okei.py` (таблица: код, обозначения/синонимы, размерность, множитель
   к базовой). Привязка к характеристике: (а) название/синоним характеристики в окне ±4 токена,
   (б) иначе — единственная характеристика кандидатов с совместимой размерностью.
   Габариты `AxBxC` → длина/ширина/высота (или глубина) по названиям характеристик позиции.
2. Качественные: для характеристик кандидатов — поиск значений `qualityDescription` в тексте
   (лемматизированное n-граммное совпадение, затем fuzzy ≥ 88). Да/Нет-характеристики:
   «без X» → Нет, «с X» / «X» → Да.
3. Конвертация значения в единицу КТРУ; сопоставление с допустимыми: concrete — равенство с
   допуском 1e-6; range — с учётом `greater/greaterOrEqual/less/lessOrEqual`. Граница
   интервала — по нотации КТРУ (детерминированно, причина в `reason`).

## R7. Пошаговое сужение и рекомендации

**Decision**: стадии: (1) категория, (2) поиск по названию → кандидаты, (3) фильтрация каждой
извлечённой характеристикой (позиция совместима, если у неё есть такая характеристика и значение
допустимо; отсутствующая характеристика — штраф, а не исключение), (4) ранжирование по
`score = bm25_norm + Σ совпадений − штрафы`. `resolved`: остался 1 кандидат или
top1 опережает top2 по score с запасом ≥ 0.15 и покрывает все извлечённые характеристики.
Рекомендации: для оставшихся кандидатов вычислить энтропию разбиения по каждой характеристике
(значения kind=1/единственные значения различают позиции) → 1–3 характеристики с макс.
информационным выигрышем; варианты значений = различающиеся значения у кандидатов.
`not_found`: 0 совместимых → рекомендация «исправить» конфликтующую характеристику.

## R8. Валидация ошибок

Типы: `typo`, `layout`, `unit_mismatch` (размерность единицы не совпадает с характеристикой),
`value_not_allowed` (качественное значение не из списка), `out_of_range` (число вне всех
интервалов/значений), `missing_required` (isRequired=true у итоговой/топ позиции),
`contradiction` (две разные величины для одной характеристики, или значения, указывающие
на разные категории), `unknown_characteristic`, `category_mismatch`.
Каждая issue: span, message, reason (ссылка на правило/позицию КТРУ), suggestion, severity,
`auto_applied` (true при уверенности ≥ 0.9 и единственном варианте).

## R9. Оценка качества

**Decision**: `eval/build_cases.py` генерирует кейсы из КТРУ скоупа: название (+ синоним) +
случайные допустимые значения различающих характеристик → ожидаемый код (только если
комбинация однозначна). Варианты порчи: опечатка, раскладка, другие единицы (г↔кг, см↔мм),
значение вне диапазона, пропуск характеристик (ожидается `ambiguous`). Плюс 150 реальных
описаний из xlsx для метрик категории и извлечения. `eval/run_eval.py` → `eval/report.md`
(top-1/top-3, F1 извлечения, P/R ошибок, p50/p95 латентность).

## R10. Фронтенд и стиль

**Decision**: Vite + React + TS, без UI-фреймворков; CSS-переменные в цветах Портала
поставщиков (основной красный `#db2b21`, тёмно-серый текст `#1f2533`, фон `#f4f5f7`, рамки
`#e1e4ea`, акцент синий ссылок `#264b82`), шрифт системный sans-serif. Шапка «Портал
поставщиков» + хлебные крошки. Debounce 400 мс → `POST /api/v1/analyze`.
**Alternatives**: SSE для каждого шага — `GET /api/v1/stream` даёт этапы для анимации воронки.

## R11. Масштабирование и деплой

**Decision**: Docker multi-stage; `backend` (uvicorn, workers=2) × N реплик, `frontend`
(nginx со статикой и proxy `/api` → backend upstream). Индекс собирается `make etl` в
`data/build/` и монтируется read-only. Горизонтальное масштабирование: `docker compose up
--scale backend=3`.
