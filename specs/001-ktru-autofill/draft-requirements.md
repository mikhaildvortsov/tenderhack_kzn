# Спецификация: Автозаполнение ключевых характеристик СТЕ (Tender Hack, Казань)

Источник: ТЗ + презентация «Методические материалы для участников Tender Hack».
Статус: Draft v1 — на ревью.

## 1. Цель

Интеллектуальный сервис для Портала поставщиков (zakupki.mos.ru): по свободному текстовому описанию товара определяет унифицированные характеристики, значения и единицы измерения, поэтапно сужает множество кодов КТРУ до одного итогового кода, находит и объясняет ошибки во вводе.

Категории хакатона: **одежда, мебель, инструменты**.

## 2. Исходные данные

| Источник | Что содержит | Правила |
|---|---|---|
| `КТРУ xml.zip` + `Описание структуры xml с КТРУ.docx` (стр. 133) | Позиции КТРУ: код, наименование, ОКПД2, характеристики, допустимые значения/диапазоны, единицы измерения, статус и период действия, связи с родительскими позициями | Парсим только `nsiKTRUNew_all-actual_*.xml`; `*_not-actual_*.xml` игнорируем |
| `Инструменты.xlsx`, `Мебель.xlsx`, `Одежда.xlsx` | Фактические характеристики и значения по СТЕ либо типовые свойства по категориям | **Приоритет у справочника КТРУ**; выгрузки — вспомогательные (синонимы, частотность значений, обучающие/тестовые кейсы) |

Пример позиции КТРУ: `25.73.30.141-00000001` «Молоток», ед. изм. «Штука»; характеристики: «Безынерционный» (Да/Нет), «Длина рукоятки» (диапазоны в мм), «Масса молотка» (диапазоны в кг); каждая характеристика может быть необязательной.

## 3. Ограничения (жёсткие)

1. Linux + веб-интерфейс.
2. Запрещены: платные поисковые API (Yandex Search, Google Custom Search); API проприетарных LLM (OpenAI, Gemini, Claude и т.п.); low-code/no-code.
3. Только открытые ML-модели, суммарный VRAM инференса **≤ 40 ГБ**; предпочтение лёгким и быстрым моделям. Необоснованно тяжёлая модель снижает оценку.
4. Допустимы LLM-роутеры (timeweb, selectel), предпочтительно отечественные — только с открытыми моделями.

## 4. Пользовательские сценарии

- **US-1.** Ввожу описание на естественном языке (в т.ч. с опечатками и неполными данными) → получаю унифицированные характеристики, значения, единицы измерения и код КТРУ.
- **US-2.** Вижу, как множество кандидатов КТРУ сужается по мере ввода характеристик; если код неоднозначен — получаю уведомление с конкретными шагами (что добавить/исправить).
- **US-3.** Получаю автоматические уведомления об ошибках (опечатки, явные несоответствия, несуществующие значения) с указанием места и обоснованием, какие характеристики некорректны и какие добавить.
- **US-4.** Вижу в интерфейсе, какие характеристики унифицированы, какие значения/единицы сопоставлены, и отслеживаю подбор КТРУ в реальном времени.

## 5. Функциональные требования

### 5.1 Разбор описания и унификация
- **FR-1.** Нормализация текста: регистр, раскладка, лишние символы, транслит, склейка/разрыв слов.
- **FR-2.** Определение категории и кандидатов КТРУ по описанию (гибридный поиск: лексический + эмбеддинги).
- **FR-3.** Извлечение пар «характеристика — значение — единица» из текста (NER/правила + лёгкая открытая модель).
- **FR-4.** Сопоставление с характеристиками выбранных/кандидатных позиций КТРУ (синонимы, морфология).
- **FR-5.** Приведение значений к каноническому виду: единицы (см→мм, г→кг, л/мл), числа (запятая/точка), диапазоны → интервалы КТРУ, булевы (да/нет/есть/без).
- **FR-6.** Для каждой унификации хранить: исходный фрагмент, результат, уверенность, источник правила.

### 5.2 Пошаговое сужение КТРУ
- **FR-7.** Для каждой введённой характеристики пересчитывать множество кандидатов; отдавать на каждом шаге: список, размер, отсекающие характеристики.
- **FR-8.** Итог: ровно один код → «определено» с уверенностью; >1 → «неоднозначно»; 0 → «не найдено».
- **FR-9.** При неоднозначности: показать, какие характеристики сильнее всего разделяют оставшихся кандидатов (information gain), и предложить 1–3 конкретных вопроса/шага («Укажите длину рукоятки: 200–300 мм или 300–400 мм»).
- **FR-10.** Учитывать статус и период действия позиции (неактуальные не предлагаются).

### 5.3 Обнаружение и исправление ошибок
- **FR-11.** Типы ошибок: опечатка в названии характеристики/значения; несоответствие единицы (длина в кг); значение вне допустимых значений/диапазонов КТРУ; характеристика отсутствует у позиции; противоречие между характеристиками; отсутствие обязательной характеристики.
- **FR-12.** Для каждой ошибки: фрагмент, тип, предлагаемое исправление (автоприменяемое при высокой уверенности, иначе — с подтверждением), обоснование на русском со ссылкой на правило КТРУ.
- **FR-13.** Пользователь может принять/отклонить исправление; результат пересчитывается.

### 5.4 Веб-интерфейс
- **FR-14.** Одно поле ввода + живая подсветка распознанных фрагментов в тексте.
- **FR-15.** Панель характеристик: таблица «характеристика / значение / ед. / статус (ok, исправлено, ошибка, не хватает)».
- **FR-16.** Панель сужения КТРУ: счётчик кандидатов, воронка по шагам, итоговый код с карточкой.
- **FR-17.** Панель ошибок и рекомендаций с кнопками «применить / игнорировать».
- **FR-18.** Обновление в реальном времени (debounce ≤ 300 мс, потоковые ответы SSE/WebSocket).
- **FR-19.** Стиль — по UI-киту Портала поставщиков (Figma из презентации).

### 5.5 API
- **FR-20.** `POST /api/v1/analyze` — описание → характеристики, кандидаты, ошибки, рекомендации.
- **FR-21.** `GET /api/v1/ktru/{code}` — карточка позиции.
- **FR-22.** `GET /api/v1/stream` (SSE) — шаги подбора в реальном времени.
- **FR-23.** `GET /health`, OpenAPI-схема.

## 6. Нефункциональные требования

| ID | Требование | Целевое значение (проверяемое) |
|---|---|---|
| NFR-1 | Латентность `analyze` (p95) | ≤ 1.5 с на CPU-пути, ≤ 3 с с ML-моделью |
| NFR-2 | VRAM | ≤ 40 ГБ суммарно; целевой запас — ≤ 16 ГБ |
| NFR-3 | Масштабирование | Stateless API, горизонтальное масштабирование; индекс КТРУ — отдельный сервис/хранилище; docker-compose + возможность k8s |
| NFR-4 | Воспроизводимость | Запуск одной командой, ETL справочника — идемпотентный |
| NFR-5 | Объяснимость | У каждого решения есть причина, видимая в UI |
| NFR-6 | Зависимость от внешних API | Нет — работает офлайн |

## 7. Предлагаемая архитектура (для утверждения в плане)

```
Browser (SPA) ──SSE/REST──▶ API (FastAPI)
                              ├─ Normalizer
                              ├─ Extractor (rules + small NER)
                              ├─ Retriever (BM25 + эмбеддинги → вектор. индекс)
                              ├─ Unifier (units, ranges, enums)
                              ├─ Narrower (фильтрация + info-gain)
                              └─ Validator (ошибки + обоснования)
ETL: KTRU XML → нормализованная схема → Postgres + вектор. индекс
```

Предварительный стек (ADR на подтверждение): Python 3.11, FastAPI, PostgreSQL + pgvector (или Qdrant), RapidFuzz/pymorphy3 для опечаток и морфологии, мультиязычный компактный эмбеддер (напр. `multilingual-e5-small`/`bge-m3`), опционально малая открытая LLM (≤ 8B, квантованная) для сложных случаев; фронт — React/Vite или лёгкий SPA; Docker.

## 9. Тестирование

- **Эталонный набор:** ≥ 150 кейсов (по ~50 на категорию) из xlsx-выгрузок + синтетика.
- **Классы кейсов:** полные данные; неполные; с опечатками; неверные единицы; значение вне диапазона; противоречия; неоднозначный КТРУ; несуществующая характеристика.
- **Метрики:** top-1/top-3 accuracy КТРУ; F1 извлечения характеристик; precision/recall детекции ошибок; доля корректных автоисправлений; p95 латентность.
- **Уровни:** unit (унификация, парсинг диапазонов), integration (ETL → индекс → API), e2e (UI-сценарии).
- Целевые пороги — определить после первого прогона на данных (см. открытые вопросы).

## 11. Границы

- **Всегда:** сверяться со справочником КТРУ как с приоритетным источником; объяснять каждое исправление; тесты перед коммитом.
- **Спросить сначала:** добавление тяжёлых моделей/зависимостей; смена хранилища; расширение за пределы трёх категорий.
- **Никогда:** вызывать проприетарные LLM/платные поисковые API; использовать `not-actual` позиции; молча «додумывать» значение без пометки уверенности; коммитить секреты.

## 12. Допущения

1. Входной язык — русский; ввод — одна позиция за раз (пакетный режим — вне MVP).
2. Датасеты с Яндекс.Диска будут скачаны командой; структура xlsx пока не изучена.
3. «Критерии_оценки_для_методички_участникам» из приложенных материалов уточнит веса — файла в корне нет.
4. Размещение в рамках одного сервера с GPU ≤ 40 ГБ или CPU-only деградация.

- `data/КТРУ/xml_all/` — 82 файла `nsiKTRUNew_all_actual_*.xml`, ~982 МБ, **81 465 позиций** (по всем отраслям, фильтрация по ОКПД2 нужна).
- Ориентир по ОКПД2 (число вхождений кода): `14.*` одежда ≈ 9 149; `31.*` мебель ≈ 6 313; `25.7*` инструменты ≈ 2 716 (`25.73` ≈ 848).

- Характеристика: `code`, `name`, `type`, `kind`, `actual`, `isRequired`, `choiceType`, `values/value` (`valueCode`, `valueFormat`, `valueSet/concreteValue` | диапазон, `qualityDescription` для качественных, `OKEI` для единиц).
- `qualityDescription` — текстовые значения (напр. «Кулачок»); числовые — через `valueSet` (конкретные значения/интервалы). Нужно разобрать `type`/`kind`/`choiceType` по `Описание структуры xml с КТРУ.docx` (стр. 133).
- `data/Примеры выгрузок/` — xlsx по трём категориям (структура пока не разобрана).
- `data/Критерии_оценки_для_методички_участникам_Казани_20261006.docx` — детальные критерии; прочитать и сверить с разделом 8.
