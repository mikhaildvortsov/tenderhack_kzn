# Feature Specification: Автозаполнение характеристик СТЕ по КТРУ

**Feature Branch**: `001-ktru-autofill`

**Created**: 2026-10-10

**Status**: Draft

**Input**: User description: "Сервис автозаполнения ключевых характеристик СТЕ для Портала поставщиков (zakupki.mos.ru). Пользователь вводит свободное текстовое описание товара (с опечатками и неполными данными) категорий: одежда, мебель, инструменты. Система определяет характеристики, сопоставляет значения и единицы измерения, приводит к унифицированному виду по справочнику КТРУ, поэтапно сужает множество кодов КТРУ до одного итогового; при неоднозначности уведомляет и предлагает конкретные шаги. Распознаёт и исправляет ошибки с обоснованием. Веб-интерфейс в реальном времени."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Описание товара → характеристики и код КТРУ (Priority: P1)

Поставщик вводит описание товара свободным текстом (например, «молоток слесарный 500 г, ручка 30 см, без отдачи») и получает список унифицированных характеристик со значениями и единицами измерения, а также код позиции КТРУ.

**Why this priority**: Это основная ценность сервиса — без неё остальные сценарии бессмысленны; сама по себе даёт рабочий MVP.

**Independent Test**: Ввести описание из справочника КТРУ (по каждой из трёх категорий) и проверить, что возвращены ожидаемые характеристики, значения в единицах КТРУ и верный код.

**Acceptance Scenarios**:

1. **Given** описание товара категории «инструменты» с полным набором характеристик, **When** пользователь отправляет текст, **Then** система показывает характеристики, значения в унифицированных единицах и один код КТРУ.
2. **Given** описание, где масса указана в граммах, а справочник использует килограммы, **When** система обрабатывает текст, **Then** значение приводится к единице КТРУ и попадает в соответствующий допустимый интервал, а исходная запись сохраняется в карточке.
3. **Given** описание категории «одежда» или «мебель», **When** пользователь отправляет текст, **Then** сервис возвращает результат того же вида, что и для инструментов.

---

### User Story 2 - Пошаговое сужение КТРУ и подсказки при неоднозначности (Priority: P1)

По мере добавления характеристик пользователь видит, как сокращается список кандидатов КТРУ. Если однозначно определить код нельзя, система сообщает об этом и называет конкретные шаги: какую характеристику добавить или уточнить.

**Why this priority**: Прямое требование задачи; определяет качество итогового кода и пользовательский опыт при неполных данных.

**Independent Test**: Подать неполное описание, зафиксировать число кандидатов, добавить характеристику и убедиться, что число уменьшилось, а подсказка указывает на характеристику, реально различающую оставшихся кандидатов.

**Acceptance Scenarios**:

1. **Given** описание, подходящее под несколько позиций КТРУ, **When** система обработала ввод, **Then** пользователь видит число и список кандидатов, статус «неоднозначно» и 1–3 конкретных шага (например, «Уточните длину рукоятки: 200–300 мм или 300–400 мм»).
2. **Given** уже показаны кандидаты, **When** пользователь дополняет описание новой характеристикой, **Then** список кандидатов пересчитывается и показывает, какие позиции были исключены и по какой характеристике.
3. **Given** характеристики, подходящие ровно под одну позицию, **When** обработка завершена, **Then** статус «код определён» и показан итоговый код с карточкой позиции.
4. **Given** характеристики, не подходящие ни под одну позицию, **When** обработка завершена, **Then** статус «не найдено» и пользователю предложены шаги по исправлению ввода.

---

### User Story 3 - Обнаружение и исправление ошибок с обоснованием (Priority: P1)

Система находит в описании опечатки, несоответствия и несуществующие значения, показывает, где именно ошибка, предлагает исправление и объясняет причину со ссылкой на правило справочника.

**Why this priority**: Отдельный критерий оценки; без него пользователь не доверяет автозаполнению.

**Independent Test**: Подать набор описаний с заведомыми ошибками каждого типа и проверить обнаружение, предложение и обоснование для каждого.

**Acceptance Scenarios**:

1. **Given** описание с опечаткой в названии характеристики или значения, **When** система обрабатывает текст, **Then** ошибка подсвечена, предложено исправление и показано обоснование.
2. **Given** значение вне допустимых значений/диапазонов позиции КТРУ, **When** обработка завершена, **Then** пользователь видит, какое значение недопустимо, какие допустимы и почему.
3. **Given** единица, не подходящая характеристике (например, длина в килограммах), **When** обработка завершена, **Then** несоответствие помечено и предложена корректная единица.
4. **Given** отсутствует обязательная характеристика выбранной позиции, **When** обработка завершена, **Then** пользователь получает уведомление, какую характеристику необходимо добавить.
5. **Given** предложено исправление, **When** пользователь принимает или отклоняет его, **Then** результат и список кандидатов пересчитываются.

---

### User Story 4 - Наглядный интерфейс в реальном времени (Priority: P2)

Пользователь работает в веб-интерфейсе: видит распознанные фрагменты в тексте, таблицу характеристик (значение, единица, статус), воронку сужения КТРУ, список ошибок и рекомендаций; результат обновляется по мере ввода без перезагрузки страницы.

**Why this priority**: Определяет удобство и демонстрацию; функциональность US1–US3 должна работать и без «живого» режима.

**Independent Test**: Открыть интерфейс, вводить описание по частям и убедиться, что панели обновляются без явной отправки формы и без перезагрузки.

**Acceptance Scenarios**:

1. **Given** открыт интерфейс, **When** пользователь печатает описание, **Then** распознанные фрагменты, характеристики и счётчик кандидатов обновляются автоматически.
2. **Given** результат содержит ошибки и подсказки, **When** пользователь просматривает панели, **Then** каждая ошибка связана с фрагментом исходного текста и содержит кнопки «применить»/«игнорировать».
3. **Given** итоговый код определён, **When** пользователь выбирает позицию, **Then** отображается карточка с наименованием, единицей измерения и допустимыми значениями характеристик.

---

### Edge Cases

- Пустое, слишком короткое или нечитаемое описание → понятное сообщение, а не пустой результат.
- Описание не относится к трём поддерживаемым категориям → уведомление об ограничении области.
- Характеристики из разных товаров в одном описании (противоречия) → ошибка «несоответствие» с обоснованием.
- Одно значение можно отнести к нескольким характеристикам → пользователю предлагаются варианты.
- Значение на границе интервала КТРУ → однозначное правило отнесения, показанное пользователю.
- Позиции с истёкшим или неактуальным статусом → не предлагаются как итог.
- Число с десятичной запятой/точкой, разные единицы, транслит, смешанная раскладка, лишние пробелы → корректная нормализация.
- Нет ни одной распознанной характеристики → шаги: какие характеристики типичны для категории.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST принимать свободное текстовое описание товара на русском языке, в том числе с опечатками и неполными данными.
- **FR-002**: Система MUST определять категорию товара и множество подходящих позиций КТРУ по описанию.
- **FR-003**: Система MUST извлекать из текста пары «характеристика — значение — единица измерения» и сопоставлять их с характеристиками позиций КТРУ.
- **FR-004**: Система MUST приводить значения и единицы к унифицированному виду справочника КТРУ (единицы, числовой формат, диапазоны, да/нет).
- **FR-005**: Система MUST пересчитывать множество кандидатов КТРУ при каждом изменении описания и показывать, какими характеристиками исключены позиции.
- **FR-006**: Система MUST сообщать один из статусов: «код определён», «неоднозначно», «не найдено».
- **FR-007**: При статусах «неоднозначно» и «не найдено» система MUST предлагать конкретные шаги (какую характеристику добавить, какое значение уточнить или исправить).
- **FR-008**: Система MUST обнаруживать опечатки, несоответствия единиц, недопустимые значения, отсутствующие обязательные характеристики и противоречия между характеристиками.
- **FR-009**: Для каждой ошибки система MUST указывать фрагмент текста, тип ошибки, предлагаемое исправление и обоснование.
- **FR-010**: Пользователь MUST иметь возможность принять или отклонить каждое исправление; результат MUST пересчитываться.
- **FR-011**: Система MUST использовать справочник КТРУ как приоритетный источник характеристик, значений и единиц; предоставленные выгрузки используются как вспомогательные.
- **FR-012**: Система MUST учитывать только актуальные позиции КТРУ.
- **FR-013**: Интерфейс MUST отображать распознанные фрагменты, таблицу характеристик, воронку сужения КТРУ, ошибки и рекомендации и обновляться по мере ввода без перезагрузки.
- **FR-014**: Для каждого результата (характеристика, унификация, исправление, шаг сужения) система MUST показывать причину решения и уровень уверенности.
- **FR-015**: Система MUST работать с категориями «одежда», «мебель», «инструменты».
- **FR-016**: Система MUST давать результат без обращения к внешним платным или проприетарным сервисам (см. конституцию проекта).

### Key Entities

- **Описание товара**: исходный текст пользователя и его нормализованная форма.
- **Позиция КТРУ**: код, наименование, категория, статус и период действия, единица измерения, набор характеристик, связи с родительскими позициями.
- **Характеристика КТРУ**: название, признак обязательности, допустимые значения или диапазоны, единица измерения.
- **Извлечённая характеристика**: фрагмент текста, сопоставленная характеристика КТРУ, исходное и унифицированное значение, единица, статус, уверенность.
- **Ошибка**: тип, фрагмент, предлагаемое исправление, обоснование, статус (принято/отклонено).
- **Шаг сужения**: набор кандидатов до и после, характеристика-причина, исключённые позиции.
- **Рекомендация**: действие для пользователя (добавить/уточнить/исправить) с указанием характеристики.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На эталонном наборе реальных кейсов из предоставленных выгрузок доля верно определённых кодов КТРУ при полном описании не ниже 90%, а в топ-3 кандидатов — не ниже 97%.
- **SC-002**: Не менее 85% характеристик в эталонных кейсах извлекаются и унифицируются корректно (значение и единица).
- **SC-003**: Не менее 90% заведомо внесённых ошибок (опечатки, неверные единицы, недопустимые значения, пропуски) обнаруживается, при доле ложных срабатываний не более 10%.
- **SC-004**: Для каждого неоднозначного результата пользователь получает хотя бы один конкретный шаг, после выполнения которого число кандидатов уменьшается, в 95% случаев.
- **SC-005**: Результат анализа появляется в интерфейсе не позднее чем через 2 секунды после остановки ввода в 95% запросов.
- **SC-006**: Новый пользователь без инструкции получает код КТРУ для типового товара не более чем за 2 минуты (проверка на демонстрации).
- **SC-007**: При росте нагрузки в 5 раз доля запросов, уложившихся в 2 секунды, не падает ниже 90% при добавлении обслуживающих ресурсов.

## Assumptions

- Целевые пользователи — поставщики на Портале поставщиков; интерфейс на русском языке.
- Область v1 — три категории: одежда, мебель, инструменты; пакетная загрузка файлов — вне v1.
- Справочник КТРУ и xlsx-выгрузки предоставлены организаторами; при расхождении приоритет у КТРУ.
- Анализируется одна позиция за запрос; хранение истории и учётные записи пользователей — вне v1.
- Целевые пороги (SC-001…SC-004) уточняются после первого прогона на эталонных данных.
- Ограничения на технологии и ресурсы определяются конституцией проекта и рассматриваются на этапе плана.
- Развёрнутый технический черновик сохранён в `draft-requirements.md` и используется как вход для `/speckit-plan`.
