# Вопросы жюри и ответы

1. **Почему не LLM?** Правила хакатона разрешают только открытые модели, а задача детерминированная: справочник закрыт. Конвейер без LLM даёт воспроизводимость, объяснимость (каждая ошибка со ссылкой на правило КТРУ), миллисекунды на CPU и 0 ГБ VRAM. Опционально подключается e5-small (118M) для эмбеддингов.
2. **Как масштабировать?** Реплики FastAPI stateless, индекс read-only в памяти (фактически ~190 МБ RSS, лимит 2 ГБ), nginx балансирует. Нагрузка растёт -> добавляем реплики, общего состояния и GPU-очередей нет.
3. **Точность и как мерили?** Эталонный набор в `eval/cases` (выгрузки СТЕ + синтетические искажения): Top-1/Top-3 по коду, F1 характеристик, recall/precision ошибок, p95. Цифры: 95.2% (top-3 97.3%), 80.0%, 92.8% (eval/report.md).
4. **Как обновляется КТРУ?** ETL: XML ЕИС -> фильтр ACTIVE и категорий -> SQLite -> индекс; запуск по расписанию или вручную, реплики перезагружают read-only индекс (rolling restart). Следующий шаг: прямой API ЕИС.
5. **Как добавить новые категории?** Это конфигурация ETL (список категорий/родительских групп КТРУ) и пересборка индекса; код не меняется. Правила валидации берутся из данных КТРУ, словарь опечаток строится из справочника.
6. **Какое железо и VRAM?** 0 ГБ VRAM (лимит 40 ГБ), обычный Linux-сервер, CPU, RAM: измерено ~190 МБ RSS на процесс uvicorn с загруженным индексом (запас до 2 ГБ на реплику). Docker-compose.
7. **Скорость?** Цель p95 не более 300 мс, >= 50 RPS на реплику; фактически: p95 6.4 мс на одиночном запросе (eval, 749 кейсов); под нагрузкой 1000 запросов analyze в 8 потоков, один процесс uvicorn: ~570 RPS, p50 14 мс, p95 20 мс, p99 31 мс (клиент и сервер на одной машине, macOS). BM25 и fuzzy по in-memory индексу, без сетевых вызовов на горячем пути.
8. **Что если КТРУ неоднозначен?** Не угадываем: показываем кандидатов, воронку сужения и рекомендации по информационному выигрышу (какую характеристику уточнить, чтобы максимально поделить кандидатов). Код выдаётся только при однозначности.
9. **Как исправляются опечатки без LLM?** Нормализация, словарь токенов КТРУ, расстояние Дамерау-Левенштейна/fuzzy с порогом и частотой термина; раскладка (RU/EN) определяется транслитерацией клавиатуры и проверкой попадания в словарь. Всегда показываем замену и причину, пользователь принимает или отклоняет.
10. **Безопасность?** Stateless, персональных данных нет, ввод валидируется (pydantic, лимит длины), параметризованные запросы SQLite, индекс read-only, внешних API нет, данные не покидают контур. Rate limit на nginx.
11. **Как интегрировать в портал?** REST `POST /api/v1/analyze` (+ SSE `/stream`, `/health`); встраивается в форму СТЕ как виджет или вызов бэкенда; формат JSON описан OpenAPI.
12. **Отличие от полнотекстового поиска?** Поиск возвращает список; мы нормализуем ввод, извлекаем и унифицируем характеристики (ОКЕИ), сужаем кандидатов по ним, валидируем по правилам и говорим, чего не хватает.
13. **Как работает проверка единиц и диапазонов?** Единицы приводятся к ОКЕИ-справочнику КТРУ (г/кг, мм/см); если размерность не совпадает - `unit_mismatch`; значение вне интервала или списка - `out_of_range`/`value_not_allowed` с обоснованием.
14. **Ложные срабатывания?** Пороги подобраны по eval, исправление всегда предложение, не автоподстановка; confidence виден; ошибки можно отклонить. Ложные срабатывания считаем в отчёте.
15. **Что не сделано / ограничения?** Скоуп v1: одежда, мебель, инструменты (~15-20 тыс. из 81 тыс.). Дальше: все категории, обучение ранжирования на разметке, автообновление КТРУ из ЕИС, встраивание в портал.
16. **Почему SQLite, а не Postgres/Elastic?** Индекс read-only, 81 тыс. позиций помещаются в память; SQLite без внешних зависимостей упрощает деплой. При росте - Postgres/OpenSearch без изменения контрактов.
